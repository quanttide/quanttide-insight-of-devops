# 发布阶段 — 巡视记录

> 巡视日期：2026-07-07

## 矛盾

正式版发布时，工具以最新预发布 tag 为比较基准，而不是上一个正式版。这不是一个实现 bug，而是一个设计假设的体现：**工具假设每次发布之间都有新提交**。但正式版发布恰恰是例外——它是在预发布系列无新提交时做的阶段晋级。

更深层的问题是：预发布周期的所有变更（alpha→beta→rc）已经被 CHANGELOG 记录过，git log 只是这些内容的原材料。**正式版 CHANGELOG 的内容来源应该是预发布 CHANGELOG 条目，而不是 git log。**

## 本质

- 工具擅长"增量"——在有新提交时正确工作
- 正式版发布是"汇总"——需要合并已有信息，而非产生新信息
- 两种场景需要的输入不同，但当前工具只用一种输入（git log）

## 追问

- 是否所有"阶段晋级"（alpha→beta→rc→正式）都应该从已有 CHANGELOG 汇总，而不是从 git log 生成？
- 如果答案是肯定的，那 `collect_git_log` 的定位是否需要重新思考——它只在有真正新提交的增量发布中有意义？

## 本地 vs 云端

### 应该保留在本地/命令行的功能

- **增量发布**——有真实新提交时，在开发者本地完成版本 bump、CHANGELOG 追加、tag 创建。这是开发者最常做的操作，延迟敏感，不需要网络。
- **发布前检查**——`release audit` 在本地即可完成 6+1 项中的大部分（版本号、配置文件、工作区、标签冲突），只有远程可达性和 GitHub Release 需要网络。
- **开发者确认交互**——`--yes` 标记让自动化跳过确认，但默认交互式确认应该在本地。

### 应该迁移到云端的

- **批量修复**——AI 绕过后产生的海量 artifact 不一致（tag 有 release 无、CHANGELOG 缺等），本地逐个处理效率低，云端可以批量扫描全部 scope 并自动收敛。
- **跨仓库协调**——当前发布只处理单个子模块的 tag/release。父仓库的子模块指针更新、关联仓库的版本依赖更新，这些跨仓库操作适合云端编排。
- **审计日志与可观测性**——谁在什么时候绕过了流程、产生了什么不一致、如何修复的，这些记录需要持久化存储，本地无法提供。
- **LLM 调用**——CHANGELOG 汇总、版本号决策等需要 LLM 的场景，在云端可以统一管理 API key、缓存结果、控制成本。

### 分界线

判断一个功能应该放在哪里的标准：**是否需要全局视角或持久状态**。

- 只需看当前工作区就能决定的 → 本地命令
- 需要看所有 scope/所有 tag/所有 release 才能决定的 → 云端
- 只需一次操作就能修复的 → 本地命令
- 需要批量收敛大量不一致的 → 云端
